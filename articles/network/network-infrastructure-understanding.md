<h1 style="text-align: center;">회사에서 운영 중인 환경으로 네트워크 이해하기</h1>
회사망에서 시작한 요청이 FortiGate와 Nginx를 거쳐 컨테이너에 도착하기까지

## 들어가며: 회사 안에서도 왜 공인 IP로 접속할까?

외부에 서비스를 제공할 서버 환경을 직접 구축하면서, 기존 회사망과 별도로 회선과 FortiGate 방화벽을 사용하는 서버망을 구성함.
팀에 할당된 공인 IP 하나를 운영·개발 서비스가 함께 사용하고, 개발 서버의 관리 접근은 회사에서만 허용한다는 조건도 함께 고려해야 했음.

현재 회사망과 서버망 사이에 사설 IP로 직접 통신할 수 있는 라우팅이나 VPN을 도입할 수 없는 상태임. 이 구성에서는 회사 PC(회사망)에서 서버에 접속하려면 FortiGate의 공인 IP를 경유해야 하는 불편한 상황임. SSH 접속은 외부 포트와 내부 서버를 연결하고 허용 출발지를 제한하며, 웹 서비스는 도메인과 FortiGate·Nginx의 전달 규칙을 통해 연결하도록 구성함.

기존에는 Proxmox로 나눈 서버 환경에서 운영과 개발을 함께 관리했고, 이후 별도의 개발 서버를 추가하면서 개발 환경을 이관했음.
이관 작업도 기존의 망 분리와 접근 조건을 유지한 채 진행했으므로, 새 서버에 맞는 VIP와 방화벽 정책, 서비스 연결 설정을 반영해야 했음.

> 공개용 예시 표기: IP는 `PUBLIC_IP`, `COMPANY_EGRESS_IP`, `DEV_SERVER_01_IP`, `DEV_SERVER_02_IP`, `OPERATIONS_SUBNET`, `DEV_SUBNET`처럼 역할 이름으로 대체함. 도메인·계정명·서비스 식별자도 예시 값으로 정리했으며, 포트 번호는 전달 관계를 설명하기 위한 예시로 읽어야 함. 명령 실행 시에는 각 값을 대상 환경에 맞게 바꾸어 사용함.

## 먼저 전체 네트워크의 경계를 살펴보기

먼저 회사 PC가 있는 망과 웹팀 서버가 있는 망을 구분함.
같은 회사에서 사용하는 장비라도, 서로 다른 방화벽 뒤에 있고 사설망 사이의 연결 경로가 없다면 내부 IP로 바로 통신할 수 없음.

현재 네트워크의 논리적 구성은 다음과 같음.
통신사 측 물리 회선 수와 상위 장비의 연결 방식은 별도 확인이 필요하므로, 여기서는 두 망의 경계와 서버 접근 경로를 중심으로 표현했음.

```text
기존 회사망 쪽 인터넷 경계
└─ 기존 회사 방화벽 / 공인 출구 COMPANY_EGRESS_IP
   └─ 회사 PC, 기존 Git·Jenkins 등

웹팀 서버망 쪽 인터넷 경계
└─ FortiGate / 공인 IP PUBLIC_IP
   ├─ WAN(port1): 외부 요청 진입
   ├─ INT(port2): OPERATIONS_SUBNET 기존 운영·서버망
   └─ DEV(port3): DEV_SUBNET 신규 개발망
```

*그림 1. 물리 회선의 배치 대신, 접근 경로를 이해하는 데 필요한 망의 경계를 나타냈음.*

회사망과 웹팀 서버망 사이에는 직접 사설 라우팅이나 Site-to-Site VPN을 구성하지 않은 상태임.

VPN 도입은 검토했으나, 구축 담당자만 익숙해지는 것으로 끝나는 작업이 아니었음. 팀 전체에 새로운 접속 방식을 공유해야 하고 기존에 사용하던 방식도 달라지므로 도입이 어려웠음. 현재는 VPN 없이 FortiGate의 포트포워딩을 통해 필요한 서버와 서비스를 연결하고 있음.

기존 Git과 Jenkins는 기존 회사망에서 사용하며, FortiGate 뒤의 서버망과 구분됨.

따라서 회사 PC에서 DEV 서버에 접근할 때도 현재 주로 사용하는 경로는 다음과 같음.

```text
회사 PC
  → 회사망의 인터넷 출구
  → PUBLIC_IP의 FortiGate WAN
  → 허용된 전달 규칙과 방화벽 정책
  → DEV(port3)의 서버
```

회사라는 물리적 장소보다 요청이 들어오는 인터페이스가 정책을 결정함.

회사에서 시작한 요청도 FortiGate 입장에서는 WAN으로 들어오는 요청이므로, 회사 공인 출구 IP를 Source로 제한하는 방식과 WAN 정책을 함께 사용할 수 있음.

여기서 말하는 ‘공인 IP 하나’는 웹팀 서버들이 공유하는 `PUBLIC_IP`을 뜻함. 회사 전체에 공인 IP가 하나뿐이라는 의미나, 물리 회선이 반드시 하나라는 의미는 아님.

## 요청 하나가 서비스에 도착하기까지

웹 서비스에 접속하는 과정을 먼저 따라가 봄.

아래 경로는 FortiGate에서 HTTPS를 종료하고 Host로 내부 서버를 선택하는 **구성 예시**임.

```text
https://update.example.com
  → DNS 조회: PUBLIC_IP
  → FortiGate Virtual Server: 외부 443
  → TLS 종료 후 HTTP Host 확인
  → Real Server: DEV_SERVER_01_IP:80
  → 서버 내부 Nginx
  → update-server:9100
```

*그림 2. 이름을 IP로 찾는 단계와, 요청을 내부 서비스까지 전달하는 단계는 서로 다름.*

각 구성 요소의 역할을 나누면 다음과 같음.

| 구성 요소 | 이 경로에서 결정하는 것 |
| --- | --- |
| DNS | 도메인이 어느 IP를 가리키는가 |
| FortiGate VIP / Virtual Server | 외부 요청을 어느 내부 주소와 포트로 전달하는가 |
| Firewall Policy | 그 경계와 방향으로 들어오는 요청을 허용하는가 |
| Nginx | 도메인이나 URL 경로에 따라 어느 애플리케이션으로 전달하는가 |
| Docker 네트워크 | 컨테이너들이 어떤 이름과 내부 포트로 통신하는가 |

### DNS는 어디까지 안내하는가?

회사망 쪽 서비스와 웹팀 서버망 쪽 서비스는 다음처럼 서로 다른 공인 IP를 사용함.

```text
cs.example.com
  → COMPANY_EGRESS_IP
  → 기존 회사망 쪽 서비스

update.example.com
  → PUBLIC_IP
  → 웹팀 서버망의 FortiGate
```

이 글에서 사용하는 일반적인 DNS 이름 조회는 내부 서버의 포트까지 지정하지 않음. `https://` 주소에 포트를 생략하면 클라이언트는 기본 포트 443으로 접속하고, 이후의 내부 목적지는 방화벽과 프록시 설정이 결정함. 서브도메인 등록 절차 역시 Nginx 설정과 별개의 작업임.
