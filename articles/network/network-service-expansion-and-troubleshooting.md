<h1 style="text-align: center;">서비스 확장과 네트워크 접속 문제 점검하기</h1>
<p style="text-align: center;"><em>서비스 추가에 필요한 설정과 접속 실패 시 확인할 요청 경로</em><br>
<small> 아래 표는 서비스별 접근 방식을 비교한 것이며, 각 서비스가 실제로 외부에 공개되어 있다는 의미는 아님</small></p>

웹 서비스와 비HTTP 서비스를 나누어 보면 ‘서비스마다 외부 포트를 늘려야 하는가?’라는 질문에 답하기 쉬워짐. 아래 표는 서비스별 접근 방식을 비교한 것이며, 각 서비스가 실제로 외부에 공개되어 있다는 의미는 아님.

| 서비스 유형 | 이 문서에서 다루는 접근 방식 | 별도 외부 포트 |
| --- | --- | --- |
| 일반 웹 화면·API | 도메인 + 웹 Virtual Server + Nginx | 기존 웹 진입점을 공유하면 보통 불필요 |
| SSH | 서버별 VIP와 포트포워딩 | 현재 직접 매핑 방식에서는 필요 |
| PostgreSQL·Oracle | SSH 터널 또는 VPN을 통한 접근 검토 | 직접 공개하는 방식이면 별도 매핑 검토 |
| MQTT TCP | TCP VIP | 별도 매핑 검토 |
| MQTT WebSocket | HTTPS와 Nginx의 웹 경로 | 기존 443을 공유할 수 있음 |
| TURN/STUN | 사용하는 TCP·UDP 포트와 릴레이 범위에 맞춘 정책 | 프로토콜과 구성에 따라 필요 |
| Proxmox 관리 화면 | VPN 또는 제한된 관리용 진입점 | HTTPS 프록시 등 선택한 방식에 따라 다름 |

### 웹 서비스를 추가하는 경우

기존 웹 진입점을 공유하는 구성이라면 도메인 등록, 필요한 인증서 이름, Host에 맞는 Real Server, Nginx 서버 블록과 컨테이너 연결을 확인함. 요청을 받을 방화벽 정책과 기존 서비스에 미치는 영향도 함께 봄.

### 현재 방식으로 SSH 대상을 추가하는 경우

서버 IP 할당 후 주소 객체와 VIP를 만들고, `WAN → DEV` 정책에 필요한 대상과 허용 출발지를 반영함. 이어 외부 포트와 내부 서버의 대응 관계를 기록함. 회사 출구 IP를 제한해도 두 사설망이 직접 연결되는 것은 아님.

### 포트포워딩이 필요하지 않은 내부 통신

모든 내부 통신이 공인 IP를 거칠 필요는 없음. FortiGate에 연결된 INT와 DEV 사이에서는 경로와 허용 정책이 핵심이며, 일반적인 내부 접근에 공인 IP VIP가 필수인 것은 아님.

```text
INT의 허용된 서버
  → INT(port2) → FortiGate 정책 → DEV(port3)
  → DEV의 대상 서버와 포트
```

`INT → DEV`에서 시작하는 연결을 허용해도 `DEV → INT`에서 새로 시작하는 연결이 자동으로 허용되는 것은 아님. 허용된 연결의 응답 트래픽과 반대 방향에서 시작하는 새 연결을 구분해야 함.

현재 사용하는 접근 경로와 비교할 수 있는 방식으로는 회사망과 DEV망의 사설 라우팅, Site-to-Site VPN, SSH Bastion 경유, 작업 PC의 DEV망 직접 연결이 있음. 이들은 현재 구성 완료된 경로가 아니며, 적용하려면 허용 범위와 관리 책임을 별도로 정해야 함.

## 접속이 안 될 때 요청 경로를 확인하기

외부 접속 실패를 살펴볼 때도 앞서 그린 경로를 기준으로 확인 위치를 나눌 수 있음. 아래는 경로별 확인에 사용할 수 있는 명령 예시임. 실행 결과를 제시하는 것은 아니며, Linux 셸 기준으로 서비스 이름과 포트를 대상 환경에 맞춰 사용함.

| 단계 | 확인할 질문 |
| --- | --- |
| DNS | 도메인이 의도한 공인 IP를 가리키는가 |
| FortiGate 진입점 | 해당 VIP나 Virtual Server가 대상 IP·포트를 받는가 |
| 방화벽 정책 | 실제 진입·목적지 인터페이스와 허용 조건이 맞는가 |
| 서버 | 대상 서비스가 의도한 주소와 포트에서 수신하는가 |
| Nginx | Host에 대응하는 서버 블록과 전달 대상이 있는가 |
| Docker | Nginx에서 컨테이너 이름을 해석하고 연결할 수 있는가 |
| 애플리케이션 | 요청한 경로에서 기대한 응답을 반환하는가 |

### 외부 또는 회사 PC 쪽에서 확인하기

```bash
# 도메인이 가리키는 IP 확인
nslookup portal.example.com

# SSH 전달 경로 확인
ssh -p 2224 deploy@PUBLIC_IP

# 해당 HTTP 테스트 포트가 구성된 경우 Host 분기 확인
curl -i -H 'Host: portal.example.com' \
  http://PUBLIC_IP:18082/
```

`18082`는 테스트 포트 예시임. 해당 포트의 전달 규칙이 실제로 구성된 경우에 사용함.

### 서버와 컨테이너에서 확인하기

```bash
# 예시 포트의 TCP 수신 상태 확인
sudo ss -lntp | grep -E ':(80|443|8087)([[:space:]]|$)'

# 컨테이너의 상태, 공개 포트, 네트워크 확인
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}\t{{.Networks}}'

# nginx 컨테이너가 연결된 네트워크 확인
docker inspect nginx --format '{{range $name, $_ := .NetworkSettings.Networks}}{{println $name}}{{end}}'

# nginx 컨테이너 안에서 서비스 이름 해석 확인
docker exec nginx getent hosts geocode-service

# 호스트의 로컬 HTTP 진입점이 구성된 경우 Host 라우팅 확인
curl -i -H 'Host: portal.example.com' http://localhost/
```

컨테이너의 `getent` 제공 여부와 로컬 80 포트 공개 여부에 따라 명령을 실행할 위치가 달라질 수 있음. 이름 해석 성공만으로 애플리케이션 응답까지 검증되는 것은 아님.

### 제공되는 인증서 확인하기

아래 도메인은 예시이므로 실제 확인할 도메인으로 바꾸어 사용함.

```bash
echo | openssl s_client \
  -connect service.example.com:443 \
  -servername service.example.com 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

이 명령으로 현재 제공되는 인증서의 주체, 발급자, 유효 기간과 SAN을 살펴볼 수 있음. 인증서가 제공된다는 사실만으로 자동 갱신 경로까지 확인되는 것은 아님.


## 마치며: 경로와 허용 조건을 나누어 이해하기

현재 서버 환경은 기존 회사망과 분리되어 있고, 운영·개발 서비스가 공인 IP 하나를 공유함. 이 조건에서 회사 PC의 관리 접속과 외부 사용자의 서비스 요청을 연결하기 위해 FortiGate의 전달 규칙과 방화벽 정책, 서버 내부의 Nginx·Docker 설정을 함께 구성했음. 서버를 추가하거나 개발 환경을 이관할 때도 이 접근 구조와 허용 조건을 유지하면서 대상 서버와 서비스 설정을 반영함.

이 환경에서 중요한 구분은 요청이 어디로 전달되는지와 그 전달을 허용하는지임. 여기에 웹 요청인지 다른 프로토콜인지, TLS가 어디에서 끝나는지를 더하면 개별 설정이 필요한 이유를 설명하기 쉬워짐.

구축 배경과 현재 구성을 더 구체적으로 설명하기 위해 확인할 항목은 아래에 남겨 둠. 현재 접속 경로와 그 구성을 선택하게 된 사유를 구분하며, 정리되지 않은 사유는 추정해서 채우지 않음.

| 남아 있는 항목 | 이 글에서 다룬 범위 |
| --- | --- |
| 통신사 물리 회선 수와 상위 장비 연결 | 두 방화벽 뒤의 논리적 망 경계만 표현 |
| 별도 회선·공인 IP를 배정한 배경과 도메인 관리 절차 | 배정 배경과 관리 절차는 별도 확인 필요 |
| 기존 회사 서비스의 상세 위치 | 회사망 쪽 서비스로 구분하고 상세 위치는 확인 필요 |
| 현재 운영 중인 VIP와 Virtual Server의 전환 상태 | 기존 기록과 Host 분기 구성 예시를 구분 |
| 인증서별 발급·갱신 주체 | Certbot 기록과 FortiGate ACME 조건부 설명을 분리 |
| 직접 라우팅의 도입 가능성과 VPN 운영 조건 | 팀 내 접속 방식 전환 부담은 본문에 정리하고, 구체적인 운영 조건은 별도 확인 |

설명용 구성 예시와 미확인 항목은 현재 운영 상태와 구분해 표시했음.
