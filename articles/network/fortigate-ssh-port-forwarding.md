<h1 style="text-align: center;">FortiGate의 SSH 포트포워딩과 접근 정책 이해하기</h1>
<p style="text-align: center;"><em>하나의 공인 IP 뒤에서 SSH 요청이 서버를 찾아가는 과정</em><br>
<small>외부 포트의 구분부터 VIP와 접근 정책까지</small></p>

운영·개발 서버가 늘어나도 외부에서 접속하는 공인 IP는 하나를 함께 사용했다. 새 서버에 SSH로 접속하려면 외부 포트를 정하고, FortiGate의 전달 규칙과 방화벽 정책을 함께 확인해야 했다.

이 구성을 이해할 때는 **요청을 어느 서버로 보낼지**와 **어떤 접속을 허용할지**를 나누어 보면 흐름이 선명해진다. 이 글에서는 SSH 접속 경로를 따라가며, VIP의 포트 전달과 방화벽 정책의 접근 허용이 어떻게 연결되는지 정리한다.

*본문의 주소와 포트는 전달 관계를 설명하기 위한 예시다. 실제 IP는 `PUBLIC_IP`, `DEV_SERVER_01_IP`, `DEV_SERVER_02_IP`처럼 역할 이름으로 표시한다.*

## 같은 공인 IP를 사용해도 접속 방식은 다르다

회사 PC와 서버가 같은 회사 안에 있어도 사설 IP로 직접 통신할 수 있는 것은 아니다.

이 환경에서는 회사망과 서버망 사이에 사설 라우팅이나 VPN이 없으므로, 회사 PC의 관리 접속도 FortiGate의 공인 IP를 거친다.

즉, 회사 안에서 운영·개발 서버에 접속하더라도 직접 사설망으로 접근하는 것이 아니라 회사망의 인터넷 출구를 거쳐 FortiGate WAN으로 들어간다. 방화벽은 이 진입 경로와 허용 출발지를 기준으로 접근을 판단한다.

| 접속 방식           | 이 글에서 사용하는 구분 기준     | 내부 목적지를 선택하는 방식               |
| --------------- | -------------------- | ----------------------------- |
| SSH             | 공인 IP와 서버별 외부 TCP 포트 | 포트포워딩 VIP가 정해진 서버의 SSH 포트로 전달 |
| HTTP·HTTPS 웹 요청 | 공통 웹 진입점과 요청한 도메인    | Host를 읽을 수 있는 프록시가 내부 목적지를 선택 |

일반적인 웹 주소의 도메인 이름을 같은 공인 IP로 연결하는 것만으로 서버별 목적지가 정해지지는 않는다.

DNS가 공인 IP를 알려준 뒤, 방화벽이나 프록시가 내부 서버를 선택할 수 있어야 한다.

SSH 연결에는 HTTP의 Host 헤더가 없으므로 여기서 설명하는 웹 도메인 분기를 그대로 적용할 수 없다. 현재의 직접 포트 전달 방식에서는 서버마다 외부 SSH 포트를 다르게 사용한다. 웹 요청을 나누는 구성은 [Virtual Server 글](fortigate-https-host-routing.md)에서 이어서 다룬다.

## VIP로 외부 포트와 내부 SSH 서비스를 연결한다

FortiGate의 VIP(Virtual IP)는 외부에서 받은 주소를 내부 주소로 연결하는 설정이다. 그중 포트포워딩을 사용하는 VIP는 외부 IP·프로토콜·포트를 내부 IP·포트에 대응시킨다. 외부 포트와 내부 서비스 포트가 같을 필요는 없다. [Fortinet의 VIP 안내](https://docs.fortinet.com/document/fortigate/7.4.7/administration-guide/443514/configuring-vips)에서도 외부 주소·포트와 변환할 내부 주소·포트를 나누어 설정한다.

| 외부에서 접속할 주소 | 내부 전달 대상 | 용도 |
| --- | --- | --- |
| `PUBLIC_IP:2223/TCP` | `DEV_SERVER_01_IP:22/TCP` | 개발 서버 1의 SSH |
| `PUBLIC_IP:2224/TCP` | `DEV_SERVER_02_IP:22/TCP` | 개발 서버 2의 SSH |

두 서버 모두 내부에서는 SSH 기본 포트 22를 사용하지만, 사용자는 외부 포트 2223과 2224로 대상을 구분한다. 개발 서버 2에 접속하는 요청의 경로는 다음과 같다.

```text
회사 PC
  → 회사망의 인터넷 출구
  → FortiGate WAN: PUBLIC_IP:2224/TCP
  → 포트포워딩 VIP
  → DEV 서버: DEV_SERVER_02_IP:22/TCP
```

같은 외부 IP·프로토콜·포트를 기준으로 하는 단순 포트 전달에 내부 목적지만 두 개 적어도 요청을 서버별로 구분할 수는 없다. 내부 IP가 서로 다른 것과 외부에서 어느 서버를 선택할 수 있는지는 별개의 문제다.

이 방식에서 SSH 대상을 추가하면 서버 IP뿐 아니라 VIP 이름, 외부 포트, 내부 포트와 연결된 정책도 함께 관리하게 된다. ‘새 서버마다 포트를 추가해야 하는가?’라는 질문은 현재 서버별 직접 포트포워딩을 사용한다는 조건과 연결된다. Bastion이나 VPN을 경유하는 방식은 다른 접근 구조이므로 여기서 이미 적용된 것으로 다루지는 않는다.

## 방화벽 정책은 그 경로를 누가 사용할지 결정한다

VIP가 전달 대상을 정했다면, 방화벽 정책은 어떤 출발지의 요청을 어느 인터페이스로 통과시킬지 결정한다. VIP를 만들었다고 접근까지 허용되는 것은 아니다. 이 글에서 다루는 일반적인 VIP 정책 구성에서는 해당 VIP를 방화벽 정책의 목적지로 연결한다.

회사에서만 개발 서버의 관리 접속을 허용하려면, 회사망의 공인 출구인 `COMPANY_EGRESS_IP`를 허용 출발지로 제한하는 조건도 함께 반영해야 한다. 이 제한은 회사망과 서버망 사이에 사설 경로를 만드는 설정이 아니라, WAN으로 들어오는 요청 중 통과시킬 출발지를 정하는 설정이다.

| 확인 항목 | 이 예시에서 살펴볼 내용 |
| --- | --- |
| 진입 인터페이스 | 회사 PC의 요청이 WAN(port1)으로 들어오는가 |
| 목적지 인터페이스 | 실제 서버가 연결된 DEV(port3)로 전달되는가 |
| Source | 회사 공인 출구 등 허용할 출발지로 제한되어 있는가 |
| Destination | 대상 서버의 SSH 포트포워딩 VIP를 참조하는가 |
| Service / Action | VIP의 변환 설정에 맞는 프로토콜·포트가 허용되는가 |
| 내부 서비스와 응답 경로 | 서버에서 SSH를 수신하고, 응답이 FortiGate를 거쳐 돌아갈 수 있는가 |

기존 정책이 `WAN → INT(port2)`용인데 새 서버는 DEV에 있다면, 내부 IP만 추가하는 것으로 충분하지 않을 수 있다. 주소 객체, VIP의 외부 인터페이스와 정책의 진입·목적지 인터페이스를 함께 확인해야 한다.

접속에 실패했을 때도 같은 순서로 범위를 나눌 수 있다. 먼저 외부 포트가 올바른 VIP를 가리키는지 보고, 이어 정책 허용과 서버의 SSH 수신 상태를 확인한다. 방화벽을 통과했는지와 실제 SSH 로그인에 성공했는지도 구분해야 전달 경로의 문제를 계정·인증 문제와 섞지 않을 수 있다.
