# 공인 IP 하나에서 운영·개발 HTTPS를 분리하기 어려운 이유

## 인증서보다 먼저 확인해야 했던 접속 경로

개발 서버에도 운영과 동일하게 HTTPS를 적용하려고 했음. 처음에는 개발 도메인의 인증서를 발급받고, Nginx에 인증서 경로와 `listen 443 ssl`을 설정하면 되는 작업으로 생각했음.
하지만 서버가 HTTPS 요청을 받을 준비를 하는 것과, 외부 요청이 그 서버까지 도착하는 것은 구분해서 봐야 했음.

사실 예전에 정리했던 내용인데, 다시 와서 기억을 해내려고 하니 전혀 기억이 안나서 다시 처음부터 공부하면서 내용을 정리함.

현재 운영·개발 서버는 FortiGate 뒤에 있고, 외부 접속에는 공인 IP 하나를 함께 사용하고 있음. 운영 도메인과 개발 도메인의 이름은 달라도, 같은 공인 IP로 연결되면 기본 HTTPS 접속은 모두 `PUBLIC_IP:443`에 도착함.

기존 VIP는 이 요청을 운영 서버의 443번으로 전달하고 있음. 따라서 개발 서버에 인증서를 설치해도 FortiGate가 개발 서버로 요청을 보내주지 않으면 외부 HTTPS 접속은 성립하지 않음. 인증서 설정만으로 끝나지 않았던 이유가 여기에 있음.

```text
외부 HTTPS 요청
  → PUBLIC_IP:443
  → 기존 FortiGate VIP
  → 운영 서버:443
```

## 개발 서버용 VIP를 하나 더 만들면 되는가

내부 서버가 서로 다르므로 개발 서버의 443번을 대상으로 VIP를 추가하면 된다고 생각하기 쉬움. 그러나 단순 포트 전달에서 먼저 구분해야 하는 것은 내부 목적지보다 외부에서 요청을 받는 조건임.

기존 VIP와 신규 VIP에 같은 외부 IP, TCP, 외부 포트 443을 지정하면 다음처럼 입구가 겹침.

| 구분           | 외부에서 받는 주소          | 내부 전달 대상                   |
| ------------ | ------------------- | -------------------------- |
| 기존 운영 VIP    | `PUBLIC_IP:443/TCP` | `OPERATIONS_SERVER_IP:443` |
| 추가하려는 개발 VIP | `PUBLIC_IP:443/TCP` | `DEV_SERVER_IP:443`        |
운영 서버와 개발 서버의 내부 IP는 당연히 다르다. 하지만 외부에서 본다면, 지금처럼 PUBLIC IP가 하나라면, `PUBLIC_IP:443`의 입장에서는, 어느 VIP를 선택해야 하는지 정할 수가 없다.

단순 VIP는 접속 도메인을 기준으로 목적지를 나누는 설정이 아니기 때문이다. 같은 입구에 목적지만 두 개 적는 것으로 운영·개발 HTTPS가 자동 분리되지는 않는다.

## 80번에서 되던 분기가 443번에는 그대로 적용되지 않음

현재 HTTP 80번은 Virtual Server에서 HTTP Host를 기준으로 내부 서버를 선택한다.

virtual server 도입 이유는, 개발 환경과 운영 환경에서 운영되는 많은 서비스들을 개발자들이 쉽게 접근할 수 있도록 도메인 정책을 도입(VPN이 없다)한 것이다.

Host는 요청한 도메인을 나타내는 정보이므로, 운영 도메인은 운영 서버로, 개발 도메인은 개발 서버로 전달할 수 있다. 운영에서는 인증 확인 요청이 이 경로를 사용하고, 개발에서는 일반 웹·API 접속도 이 경로를 사용함.

반면 현재 443번은 Host 기반 Virtual Server가 아니라 운영 서버로 전달하는 기존 VIP이다. 즉 virtual server 기능을 이용하지 않은, 일반적인 포트포워딩이다.

이게 가능하도록 설정하는 방법은, Fortigate를 이용하는 방법이 있다. virtual server 기능을 이용하여, FortiGate가 먼저 TLS 연결을 처리하도록 구성을 하는 것이다. FortiGate가 HTTPS 요청의 암호화를 풀고, 내부의 Host(도메인)를 확인해 운영·개발 서버로 나눠 전달할 수 있음. 아직 적용한 구성이 아니라 검토 중인 방식임.

이때 FortiGate에 인증서와 개인키를 등록하고, HTTPS Virtual Server에서 도메인별 전달 대상을 정하는 방식으로 변경하게 됨.

따라서 80번 목록에 개발 서버를 추가하듯 단순히 항목만 늘리는 작업과는 다름. 외부 HTTPS를 누가 처리할지, 기존 443번 요청을 어디로 전달할지까지 함께 달라지는 구성임.

하지만 지금 구조와는 너무 달라 아직 작업을 못하고 있다.
## webroot 전환으로 해결되는 부분과 남는 부분

인증서 갱신 방식과 HTTPS 전달 경로는 목적이 다름. standalone은 Certbot이 임시 웹서버로 HTTP-01 확인 요청에 응답하고, webroot는 Certbot이 만든 확인용 파일을 기존 Nginx가 제공하는 방식임.

Nginx가 80번을 사용하는 구성에서 webroot를 적용하면, Certbot이 같은 포트를 직접 열 필요가 없어 갱신을 위해 Nginx를 중지하는 상황을 피할 수 있음. 다만 현재 운영에 HTTP→HTTPS 리다이렉트가 이미 적용되어 있다는 의미는 아님. 앞서 이야기한 포트 충돌은 앞으로 Nginx에 80번 리다이렉트를 추가하는 경우를 가정한 설명이었음.

webroot로 바꿔도 `PUBLIC_IP:443`의 전달 대상은 자동 변경되지 않음. 운영·개발 두 주소를 인증서 하나에 넣더라도, 인증서가 두 서버로 요청을 나누어 보내주는 것은 아님.

현재 조건은 추가 공인 IP가 없고, 운영 Nginx에 개발 전달 설정을 넣지 않으며, 별도 시험 환경 구성도 어려운 상태임. 따라서 남은 문제는 인증서를 구하는 것보다, 기존 운영 통신에 미치는 영향을 고려하면서 공통 443번 입구에서 운영·개발 요청을 어떻게 구분할지에 있음. 그 전환 방식은 아직 확정하지 않았음.
